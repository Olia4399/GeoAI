## 修改意见

### 1. 执行步骤折叠交互 ✅ 已修复

**意见原文**：执行步骤可折叠，折叠符号与"📋 执行步骤 (x)"同一行，水平居右；且报告生成之后默认展示折叠状态，需要用户主动打开才展示。

**排查**：
- 折叠符号与标题同行居右：`MessageList.tsx` 标题行原本已是 `display:flex + justifyContent:space-between`，符号在行尾，该点已满足，无需改动；
- 缺失点：`stepsCollapsed` 初始为 `false`（默认展开），且报告生成后仍保持展开，不满足"默认折叠、用户主动打开"。

**修复步骤**（`frontend/src/components/chat/MessageList.tsx`）：
1. `stepsCollapsed` 初始值 `false` → `true`（默认折叠）；
2. 新增 `useEffect`：`agentResponse` 更新时 `setStepsCollapsed(true)`——每次新分析完成后自动折叠；
3. 同步更新注释（"默认展开"→"默认折叠，点击标题行展开/收起"）。

**结果**：新分析完成后执行步骤卡片默认折叠（只显示标题行 + 行尾 ▶ 符号），点击标题行展开/收起；折叠符号与标题同一行、水平居右。流式过程中的步骤仍通过"心流"卡片实时可见，不受影响。

### 2. 执行步骤最后一步的 Markdown 原始内容 ✅ 已修复

**意见原文**：执行步骤的最后一步"分析完成。以下是朝阳区咖啡店选址的完整空间分析报告。 --- ## 📊 …"内部还是有 markdown 原始格式内容，可以只保留"分析完成。以下是朝阳区咖啡店选址的完整空间分析报告。"，后面具体内容不需要截取进去。

**排查**：
- 后端 [planner.py](agent/src/planning/planner.py) 的 `_parse_messages` 对 reasoning 内容做 `str(msg.content)[:500]` 硬截断，最终总结后紧跟的"--- + 报告 Markdown"被一并截进步骤内容；
- 前端 `truncateStep` 虽然剥离标题/表格/分隔线，但只保留第一句话（"分析完成。"），与期望的"保留分隔线前的总结全文"不符。

**修复步骤**：
1. 后端（源头修复，新分析生效）`agent/src/planning/planner.py`：
   - 新增 `import re`；
   - reasoning 分支改为 `re.split(r"\n\s*[-*]{3,}", content)[0].strip()` 先按 `---` 分隔线截断，再做 500 字截断。
2. 前端（兜底修复，历史记录同样生效）`frontend/src/components/chat/MessageList.tsx`：
   - `truncateStep` 先按 `\n\s*[-*]{3,}` 切分；存在分隔线时直接返回分隔线前清洗后的全文（兜底"分析完成"）；无分隔线时保持"第一句话"截断。

**结果**：新分析中该步骤内容只含"分析完成。以下是…报告。"；历史记录里已存的 500 字原始 Markdown 也会被前端截断逻辑清洗为同样的总结文本。

### 3. 列表内文字被切成"一词一框" ✅ 已修复

**意见原文**：列表内的文字容易被切分，例如"坐标"、"POI类型"等被渲染进深色代码框（`background: rgb(38, 50, 56)` 样式），一词占一行，而不是继续作为正文或将内容一起放到一个框内。

**排查**（用 node 对 react-markdown 10.1.0 实测确认）：
- 根因：react-markdown v10 **不再向 `code` 组件传 `inline` prop**（实测行内代码的 props 只有 `{node, children}`）。旧覆写 `code: ({children, inline}) => inline ? 行内样式 : 深色 pre` 中 `inline` 恒为 undefined，导致**所有行内反引号代码都走进深色块分支**——报告正文/列表里的 `坐标`、`POI类型` 等行内代码被渲染成深色 `pre` 块，每个断行显示，形成"一词一框"。
- 实证数据：`analysis_history.db` 中的真实报告（如"坐标：`39.9307, 116.4499`附近，汇集了 `The Local`…"）大量使用行内反引号，正是重灾区。

**修复步骤**（`frontend/src/components/chat/ReportRenderer.tsx`）：
1. `code` 覆写改为按 `className`（language-xxx）或 children 含换行（围栏代码块文本末尾必带 `\n`）判定块级；块级只输出透明底色 `code`（深色盒样式统一由 `pre` 承载）；
2. 新增 `pre` 覆写：深色背景（#263238）+ 绿色等宽字体 + 圆角 + overflow——即原"代码块无样式"修复的样式迁移到 `pre`；
3. 行内代码恢复浅色小胶囊样式（浅底红字），不再断行。

**结果**：报告正文与列表中的行内代码（坐标、POI 类别等）恢复为行内小胶囊，文字连续成段；真正的多行代码块仍渲染为单个深色框（内容在框内整体展示）。

### 5. 框选区域无法使用 + 图层面板补全 ✅ 已修复

**意见原文**：地图左上角"📐 框选区域"点击后在地图上点击点位/框选区域都无反应，请求也没有新发出的消息；右上角"🗂 图层"因数据未齐全图例无法显示使用，希望快速补全。

**排查**：
1. 框选失效根因：`MapView` 用 `mapRef.current`（ref）给 `DrawTool` 传地图实例。**ref 更新不触发 React 渲染**，而 `MapView` 不订阅 `mapBounds`，地图初始化后不再重渲染，`DrawTool` 拿到的 map 永远是初始的 `null`——effect 里 `if (!map) return` 直接退出，鼠标监听器从未挂载。
2. 图层面板：`layerVisibility` 只改 store，从未调用 `map.setLayoutProperty`；"分析结果/框选区域"无对应显隐逻辑；`buffer` 项无对应图层；面板无图例。

**修复步骤**：
1. `frontend/src/components/map/MapView.tsx`
   - 新增 `mapInstance` state：地图创建后 `setMapInstance(map)`、销毁时置 null；`<DrawTool map={mapInstance} />`——DrawTool 拿到真实地图实例，监听器正常挂载，框选（拖拽出矩形 → GeoJSON 入 store → 虚线框图层渲染）恢复可用。
   - 新增 `applyVisibilityRef`：遍历 `LAYERS`，按 `mapPrefix` 匹配 style 图层（`poi-label`、`road-*`、`building`、`agent-result-*`、`draw-geometry`），逐个 `setLayoutProperty(id, "visibility", visible ? "visible" : "none")`；在 style load 后、`layerVisibility` 变化时、新结果图层加入后各应用一次。
2. `frontend/src/components/map/LayerPanel.tsx`
   - `LayerDef` 增加 `mapPrefix`/`disabled` 字段并导出 `LAYERS`；图层项调整为真实可用的：POI(`poi`)/道路(`road`)/建筑(`building`)/分析结果(`agent-result`)/框选区域(`draw-geometry`)；行政区划标记 `disabled` 显示"暂无"（底图无该数据，如实标注）。
   - 底部新增"分析评分图例"：0-100 渐变条（红→橙→黄→绿→深绿，与 MapView 的 score 插值着色一致）+ 刻度说明。
3. `frontend/src/store/index.ts`
   - `layerVisibility` 初始键 `buffer` → `draw`，与图层面板同步。

**结果**：框选区域恢复正常（点击按钮 → 拖拽画框 → 虚线框 + GeoJSON 入 store，随下一次提问作为地图上下文发送；单击不生效属于 0.001° 阈值过滤误触的设计）；图层面板勾选实时显隐底图与分析结果图层，并附评分图例；行政区划如实标注暂无数据。

## 追加修复：统一报错组件与"静默失败"治理

**问题描述**：运行请求失败时没有任何输出，浏览器控制台也看不到有用信息，无法定位问题。

**排查**：
1. 后端复现：curl 流式请求全程正常（意图 → 步骤 → done 事件），说明 agent/spatial 服务本身健康，问题在前端错误处理链路；
2. 前端三条"静默吞错"路径：
   - fetch 拿到非 2xx 响应时只把原始文本塞给 `onError`，FastAPI 422 的 `detail` 是数组会被 `String()` 成 `[object Object]`；
   - 响应流提前结束（未收到 done 事件）时，`onDone` 里只 `loading=false`，**什么都不显示**——这正是"请求没有输出"；
   - 错误卡片用 `JSON.stringify(Error)` 渲染，`Error` 对象序列化结果是 `{}`，等于白屏。

**修复步骤**：
1. `frontend/src/types/index.ts`：新增统一错误结构 `AgentError`（`type` 分类 / `title` 标题 / `detail` 细节 / `hint` 排查提示 / `status` 状态码）。
2. `frontend/src/services/agent.ts`：
   - 新增 `toAgentError(err, status?)` 分类器：network（Failed to fetch）/ timeout / llm（401、api key）/ http（按状态码，含 422 校验失败）/ unknown，每种带默认排查提示；
   - `queryStream`：非 2xx 响应解析出 `detail`（422 数组自动序列化）后走 `toAgentError`；响应体为空时也报错而非静默结束；catch 分支走 `toAgentError`。
3. `frontend/src/store/index.ts`：
   - `error` 字段 `string | null` → `AgentError | null`；
   - SSE `error` 事件规范化：透传后端分类的 `error_type/title/hint`，`detail` 统一转字符串；
   - **流中断检测**：流结束但未收到 done 事件且无结果时，不再静默结束，而是置入"响应流意外中断"错误（带查看后端日志的提示）。
4. `frontend/src/components/chat/ErrorCard.tsx`（新增）：统一报错组件——按类型显示图标/标题/HTTP 状态码、技术细节（等宽字体可滚动）、💡 排查提示、可选 🔄 重试按钮。
5. 接入点：
   - `MessageList.tsx`：错误卡片替换为 `ErrorCard`，重试按钮复用最近一次 query 重新提交；
   - `HistoryPanel.tsx`：列表/详情/对比三个视图的请求失败均显示 `ErrorCard`（刷新/重试）；
   - `App.tsx` + `frontend/src/components/common/ErrorBoundary.tsx`（新增）：React 渲染异常兜底，避免整树白屏，展示错误信息与刷新按钮。
6. 后端 `agent/src/api/routes.py`：
   - 新增 `_classify_error(exc)` 异常分类：spatial（连接失败）/ llm（认证失败、限流）/ timeout / 默认 sse，各带排查提示；
   - SSE `error` 事件额外携带 `error_type/title/hint`，前端直接展示。

**验证**：`npx tsc --noEmit` 全绿；`python -m py_compile agent/src/api/routes.py` 通过；curl 实测 422 路径返回 `{"detail":[...]}`，前端解析链路已覆盖（数组序列化 + 分类提示）。

**结果**：此后任何失败（网络不通、后端 500/422、流中断、LLM 认证/超时、渲染异常）都会以分类明确的错误卡片展示：友好标题 + 技术细节 + 排查提示 + 重试按钮，替代此前的静默结束或 `{}` 白屏。若问题仍复现，按错误卡片上的提示逐项排查（如"查看 agent 服务 (8001) 控制台日志"）。

### 追加修复：LLM 请求超时治理（实测：工具调用已执行后失败）

**现象**：错误卡片显示"⏱️ 大模型请求超时"，且失败发生在工具调用执行之后（即规划续推或报告生成阶段的 LLM 调用超时）。

**排查**：三个 LLM 实例（意图解析/规划/报告）均未配置 timeout，使用 OpenAI SDK 默认 600 秒超时——LLM 服务慢响应或网络抖动时请求长时间挂起，且无重试；前端 fetch 无看门狗，后端一旦挂死前端会无限等待。

**修复步骤**：
1. 后端三个 LLM 实例统一配置 `timeout=120, max_retries=1`（`agent/src/intent/parser.py`、`agent/src/planning/planner.py`、`agent/src/reasoning/interpreter.py`）——超时从默认 600s 缩短到 120s，超时/连接错误自动重试 1 次；
2. `agent/src/api/routes.py`：
   - `event_stream` 增加 `phase` 变量跟踪（intent/planning/report），异常时随 SSE error 事件下发，并在控制台打印 `[query/stream] ERROR phase=... exc=...`；
   - 超时类 hint 更新为可操作建议（"LLM 调用超过 120 秒（已自动重试 1 次）仍失败；检查网络或 LLM 服务状态，稍后重试，或更换 agent/.env 中的 LLM_MODEL"）；
3. 前端 `agent.ts`：新增 10 分钟看门狗——`setTimeout` 到时主动 `abort()` 并上报"请求超时（前端兜底）"错误，所有出口（非 2xx/空响应/正常结束/catch）均 `clearTimeout`，`timedOut` 标志防止与 AbortError 双报；

**验证**：`python -m py_compile` 四个后端文件通过；`npx tsc --noEmit` 全绿。

**结果**：LLM 慢响应/挂起场景下，最长约 4 分钟（120s×2 次尝试）即可得到明确报错而非长时间挂起；错误卡片会标注失败阶段（意图/规划/报告）并给出可操作提示；即使后端进程整体挂死，前端看门狗也会在 10 分钟后主动中断并报错。
